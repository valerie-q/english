Exercise A — Active or passive? Rewrite

Rewrite each sentence in the opposite voice (active → passive, or passive → active).

  1. The team deployed the new feature yesterday. →
  2. The bug has been fixed by the QA engineer. →
  3. Someone will review your pull request tomorrow. →
  4. The design was rejected by the client. →
  5. They are testing the new update right now. →
  6. The server crashed twice last week. →
Answers

  2. The QA engineer has fixed the bug.
  3. Your pull request will be reviewed tomorrow.
  4. The client rejected the design.
  5. The new update is being tested right now.
  6. No passive possible — "crash" is an intransitive verb (no direct object), so it can't take a passive form.

The 6 phrases
PhraseMeaningExample
Turn outto happen / to appear to be, in the end"I thought this project was going to be easy, but it turned out to be a very difficult one."

Writing a Bug Report
Structure, sections, and your own bug report
📝
Exercise 1A — Read the text and prepare to write your own bug report

Look at the example of a good bug report. What makes it good? It's concise but doesn't miss any key details and contains all the necessary elements of a proper bug report, namely:

  1. Title / summary (missing product images)
  2. Severity/Priority
  3. Description
  4. Expected Result
  1. Actual Result
  2. Steps to reproduce
  3. Environment
  4. Visual Proof (screenshots, videos, text)

Let's take a closer look at each section of a bug report.

SectionDescription
Summary (Title)The goal is to make the report searchable and uniquely identifiable. Think of it as a subject line for emails — be specific enough to provide a complete description of the problem in a nutshell.
Bad: Bug.
Good: Error 5C79 when confirming request.
DescriptionA concise (1–2 sentences) overview of the bug itself. A good description lets the reader understand what the actual issue is and how severe it is.
Ex: The headline text size and color on the pricing page don't match the original designs.
Tip: stick to Present Simple.
Expected ResultA description of the proper behavior that should happen if the bug is fixed.
Ex: New email notification should be displayed right on the email arrival.
Tip: we tend to use passive voice — should + be (past participle) or is/are + past participle.
Actual ResultA description of the current "buggy" behavior.
Tip: for convenience, it's possible to omit "to be" ("not shown" instead of "is not shown") and articles where implied ("error displayed").
Steps to ReproduceLay out the steps in an easy-to-follow way so the developer can easily reproduce the bug.
Tip: double-check your repro steps to make sure you haven't left out any important details.
EnvironmentInclude the environment setup and configuration info — OS, system build, platform etc. Add any additional info (URL, crash data, regression range etc.) and attach all relevant files.

searchable — такий, що легко знайти пошуком

identifiable — впізнаваний, ідентифікований

in a nutshell — коротко, в двох словах

severe — серйозний, критичний (про баг)

Discussion
  1. Which section of a bug report do your developers usually complain is missing or unclear?
  2. Does your team use Present Simple or another tense when writing descriptions? Have you noticed this pattern before?
